## 2. 对产品的初步理解

核心价值应是：用户运行游戏或图形应用时，以尽量低的干扰读取帧率、帧时间和相关资源指标，并可调整显示内容与外观。它首先是性能 HUD / utility，而不是把大量卡片铺满屏幕的 dashboard。

这是依据产品名称、参考代码和图片形成的工作假设；尤其是“监测外部游戏”仍需要用户确认。不能把 GPUI 自身 UI 刷新率当成目标游戏 FPS。

### 截图功能与源码映射

| 区域 | 截图观察 | 本地 Graphy 对应行为 | Windows 迁移边界 |
| --- | --- | --- | --- |
| FPS 数值 | 当前 FPS、帧时间 ms、avg/min/max | 当前文本按短时间段聚合；最近最多 1024 帧计算平均及 low 值 | 外部进程采集入口需另行实现和验证；统计窗口必须明确 |
| FPS 图 | 紧凑历史点/柱、基准线、阈值颜色 | 环形历史、平均线、阈值线、自适应缩放 | 可以借鉴表达，不能直接搬 Unity shader 调用链 |
| 内存 | reserved/allocated/mono 数值与多色曲线 | Unity Profiler 的三项内存，字节换算 MiB | 应重新定义系统内存/目标进程内存指标，不能简单改标签 |

### 一个重要版本差异

截图中出现的是 `avg / min / max`；但当前本地源码 `G_FpsMonitor` 与 `G_FpsText` 的统计是平均值、1% low、0.1% low，而非 min/max。两类指标不能互相替换；如需全部提供，应分别定义含义和窗口。

当前 Graphy 平均 FPS 为 `样本数 / 总帧时间`，不是逐帧 FPS 数字的算术平均；low 值取最慢的一部分帧时间再求倒数。它的 1024 帧窗口在不同 FPS 下覆盖的实际时长不同。参考：Graphy 的“FPS：采样、统计窗口、文本与曲线”。

## 3. GPUI-Kit 指南带来的约束

### 设计约束

1. **任务与层级优先。** 让当前 FPS 和帧时间容易读取，次要设备信息不应抢占注意力；HUD 与设置界面可以有不同的局部密度。来源：Design“从用户任务开始”“层级”“密度层级”。
2. **主题令牌优先。** HUD 背景、前景、FPS 阈值色和内存/音频系列色应有具名语义；需要自定义角色时在产品 theme/token 层定义，不能在各个渲染位置散落 raw color。来源：Design“颜色与主题”、Coding“主题与样式”。
3. **相对尺度与精确对齐。** 数字列稳定、可比较值右对齐，必要时采用等宽/表格数字；普通布局采用 rem-based helper，物理窗口/绘制边界例外应记录。来源：Design“对齐细节”“缩放、基础字号与 rem”。
4. **保留桌面交互。** 设置使用标准 Button、Switch、Select、Menu 等组件；键盘、焦点、禁用/错误状态和浮层关闭路径不能因为 HUD 看起来简洁而丢失。来源：Design“组件与组合”“交互状态”“反馈与浮层”。
5. **缺数据必须诚实。** 等待目标、无权限、目标退出、采集失败应可区分；未知或不可用不能伪装成 0 FPS 或正常读数。此为根据 Design“状态必须可见”和 Coding“异步任务与副作用”应用到本产品的建议。

### 编码约束

1. **初始化与窗口 Root。** 官方指南示例使用 `gpui_kit::init` 和 `gpui_kit::open_window`，每窗口只有一个 Root；实际 API 必须按选定版本确认。来源：Coding“初始化与 Root 所有权”。
2. **持久状态与组件值区分。** 持续采集、历史与订阅由明确 owner 持有；有生命周期的状态用 Entity，轻量显示组合优先 RenderOnce，不为每个视觉片段创建 Entity。来源：Coding“选择正确的组成单元”。
3. **render 只描述 UI。** 不在 render 中启动采集、解析、注册无界订阅或无条件 notify；昂贵工作在后台完成，在正确 context 中提交一致状态，只通知必要 owner。来源：Coding“渲染与组合”“异步任务与副作用”“性能规则”。
4. **任务、订阅可释放。** 循环任务与 Subscription handle 有 owner，默认不 detach；关闭视图、切换目标或旧采样晚到时，应取消或拒绝过期结果。来源：Coding“限定所有权关系与订阅生命周期”“异步任务与副作用”。
5. **刷新节奏分离。** 原始采样、统计汇总、文字更新与图表绘制不必同频；UI 重绘次数不能决定目标应用的统计结果。这是结合 Graphy 已分离文本刷新与图更新，以及 Coding 的渲染/异步规则得出的迁移建议，不是某个已存在 API 的保证。
6. **按能力组织，避免过早分 crate。** 数据采集、统计、HUD、设置需要清楚职责，但小能力可以先留在 module，不能为每个页面/helper 拆 crate。平台代码放在窄能力边界后。来源：Coding“大型应用按业务能力组织 crate”“平台与能力边界”。
7. **先确认 API 再编码。** 不能把 React/CSS 或旧 GPUI 的写法猜成 GPUI-Kit API。来源：Design“AI 生成界面的规则”、Coding“编码代理规则”。

## 4. 可借鉴与不可直接移植的部分

### 可借鉴

- 紧凑分区：FPS → 内存 → 音频，设备信息独立显示。
- 环形历史缓冲、帧时间聚合、阈值线与低开销的周期性文字更新思路。
- 模块级显示模式、图表分辨率、缩放、颜色和角落锚点配置。
- 频谱的当前值与峰值衰减叠加；需清楚标出横轴为频率而非时间。

### 不可直接移植

- MonoBehaviour.Update / Time 不是跨进程 FPS 采集器。
- Unity Profiler allocated/reserved/mono 不是 Windows 通用内存分类。
- Unity AudioListener 不是系统回环音频接口。
- Unity RectTransform/Canvas/材质透明不等于桌面窗口透明、置顶或穿透。
- Unity 焦点内快捷键不等于 Windows 全局热键。

依据：Graphy 各数据源与“配置、模块状态、位置、图表着色与刷新节奏”。

## 5. 下一轮应确定或验证的事项

### 产品问题（尚未要求用户本轮回答）

- **监测对象：** 任意外部游戏、指定进程，还是应用自身？是否需要自动识别前台游戏？
- **FPS 定义：** 提交/呈现/显示的哪类帧？窗口、无边框、独占全屏分别支持到什么范围？
- **统计口径：** avg/min/max、1% low、0.1% low 哪些需要？采用会话、固定秒数还是固定帧数窗口？
- **内存口径：** 系统 RAM、目标进程工作集/私有内存、GPU 显存哪些属于首版？
- **音频对象：** 系统输出、目标进程输出或麦克风？仅电平还是还需要频谱？
- **窗口体验：** HUD 是否置顶/穿透，如何进入布局编辑，是否需要独立设置窗口与全局快捷键？

### 技术验证（本轮未做，不作为已经解决的结论）

- 选定 GPUI-Kit 版本、依赖来源、Windows 构建条件与授权条件。
- 调研并验证外部游戏 FPS 采集方案；ETW/PresentMon 只能作为后续候选方向，目前没有针对这些接口的官方资料研究或原型验证。
- 验证 GPUI-Kit 与 Windows 窗口层组合的透明、置顶、穿透、DPI、多屏和全屏能力；不能由这两份指南推定已支持。
- 根据音频范围再研究 Windows 采集接口；本轮没有验证系统回环或进程级音频能力。
- 确定可接受的 CPU/GPU/内存开销及采样丢失行为，再制定性能验收，不先编造指标。
